# 给 Muse 的部署指令（快速通道 · 低延迟版）

> 用户使用说明：把这份文件发给 Muse，对它说一句「按这份指令部署
> 微信桥的快速通道」即可。下面的内容是写给 Muse 的，你只需要配合
> 它完成注册和提供 Key。

---

## 你的任务

你是 Muse，用户的个人 AI 助手。你正在为用户部署 WeChat-bridge。除了基础桥接（见 README），你必须把回复延迟做到「低延迟标准」，并主动向用户索取快速通道所需的配置。用户是新手：凡是能由你自动完成的（填地址、选模型、写配置、写服务、测试），不要让用户做；用户只需要做两件事：按你的指引注册一家模型平台、在注册完成后把 API Key 发给你。

部署完成后，把结果存进你的记忆：用户选了哪家平台、快脑模型名、配置路径、验收耗时各是多少。今后用户说「微信桥慢了」，你先按第五步自查再回答。

**部署位置：就装在你自己的运行环境里**，与你同机常驻——桥、fastlane 都跑在你的环境中，用户不需要提供任何服务器或电脑。教程里对用户也是这样承诺的，不要反过来向用户索要主机、SSH 或部署地址。

## 第三步：写配置（三项里只有 Key 来自用户）

把项目根目录的 `fastlane_config.example.json` 复制为 `fastlane_config.json`：`base_url` 和 `model` 按第一步表格自动填，`api_key` 填用户给的 Key。`chmod 600 fastlane_config.json`，并确认它在 `.gitignore` 里。fastlane.py 会在文件变更时自动重读配置，不需要重启。

## 第四步：低延迟部署要求（硬性，不达标不算部署完成）

1. **唯一前门**：只允许 fastlane 认领 inbox/。任何分拣/值守进程只处理 escalated/，严禁第二个进程碰 inbox/——双处理器会给用户发重复回复（实测事故）。
2. **事件级触发**：fastlane 以 ≤0.3 秒轮询 inbox/（或用文件监听），认领动作必须是原子 rename 到 processing/。禁止用分钟级定时任务轮询收件箱（那会平均白等 30 秒）。
3. **分级回复**：简单问答由快模型直答；需要工具、记忆、实时数据或执行操作的，转 escalated/ 交你（主会话），且**只发一条**即时回执（「收到，这件事我来办，稍等一下。」）。快模型答不完整（被长度截断）也要转 escalated/，不许发半截答案。
4. **长连接复用＋重复问题缓存**：快模型调用复用同一条 HTTPS 长连接；完全重复的问题直接用缓存答案（模型调用 0 秒）。
5. **出箱快发**：daemon 扫描 outbox/ 的间隔 ≤0.5 秒。
6. **健康判据**：判断桥是否活着，看三样——消息队列游标（cursor）最近几分钟有没有更新、进程线程数是否为 3、日志里轮询是否持续。**只看 systemd 显示 active 会漏掉僵尸进程**（轮询线程退出而主进程假活）。

## 第五步：自测验收（做完把结果报给用户）

让用户（或你模拟投递）依次测三条微信消息并掐表报告端到端耗时：

1. 新的常识题（如「珠穆朗玛峰有多高？」）→ 应由快模型直答，**≤5 秒**；
2. 把同一道题再发一遍 → 命中缓存，**≤3 秒**；
3. 复杂任务（如「帮我把今天的开支整理成表格」）→ **1 秒内**先收到回执，你随后给出结果，且全程只有一份、不重复。

任一项不达标，按顺序排查：轮询间隔是否被改大、是否有第二个进程在抢 inbox/、快模型连接是否每次新建（无长连接复用）、快模型是否选了大模型档（换 Flash/Lite/7B 级小模型）。修好后复测再报告。

## 红线

- API Key 只存本地 `fastlane_config.json`（600 权限），不回显、不外传、不进 git。
- 不改动「唯一前门」架构去省事；发现已有分钟级分拣任务在跑 inbox/，先停用它再部署快速通道。
- 部署或自测失败就如实报告失败点，不要用「大概没问题」收尾。
